# Colony Screen Render Chain — Deep RE Trace

**Status**: Partial trace. Entry path verified; per-element render code resides in **overlay segment 0x191F**, which is NOT covered by the existing `viceroy_overlay_full.asm` disassembly.

**Generated**: 2026-05-23 from raw VICEROY.EXE bytes + `extracted/disassembly/*.asm`.

## TL;DR for the renderer

What this trace gives the Python/Godot port:

1. **`[0x8542]` is a NEAR POINTER to the active ColonyRecord** (not a nation index). The disassembler's "cur_nation" comment is WRONG. See §1.
2. **`[0x539e]` is num_colonies (current player), max 48** — not active colony index. See §1.
3. **Colony table base is DGROUP:0x5D46** (not 0x5D60). 0x5D60 = 0x5D46 + 0x1A (after the name field). See §1.
4. Click-to-enter chain: **func_L187/L206 → set_active_colony (file 0x82DC) → lcall 0x191f:0x1de**. See §2. The actual screen renderer is at **0x191F:0x1DE = file 0x35A4 area, which lives in overlay 0x191F (NOT disassembled).**
5. The LCALL thunk table at file **0x1A5F0** uses formula `target_file = 0x2400 + jmp_seg*16 + jmp_off`. Several FUNCTIONS_INVENTORY thunk descriptions were inferred wrong. See §3 for correct resolutions.
6. `func_O512`'s `cmp [bp-4], 4` is iterating the **4 cardinal-direction neighbors** (not 4 minimap quadrants). The terrain-rendering chain has NOTHING to do with the colony screen. See §4.
7. **The colony screen renderer has NOT been located in the available disassembly.** All evidence points to overlay 0x191F. See §6.

## §2. Colony screen ENTRY chain (verified)

### Step 1 — Mouse click / unit move triggers tile-action handler

**`func_L187`** at file 0x07D3E (502 bytes) — `process_unit_move_to_tile(unit_idx, target_unit_idx)`.

When user moves a unit onto a tile (or right-clicks on map):
- Reads target tile (X,Y) from `UnitRecord[target_unit_idx].+0x3144`, `.+0x3145`.
- Dispatches based on what's at the tile: sea lane, native village, enemy unit, own colony, etc.
- For own colony: `lcall 0x5eb:0xa76` (= `find_colony_at_xy` shortcut wrapper) returns colony_idx in AX.
- Then `lcall 0x5eb:0x2c` (= `set_active_colony` — see Step 2) at file 0x07E06.
- Sets bit 0x40 in `[0x8D02]` at file 0x07E18 ("own-colony was clicked").
- Returns to caller (which reads `[0x8D02]` to dispatch screen — caller is in overlay 0x191F, NOT in disasm).

### Step 2 — `set_active_colony(colony_idx)` — file 0x82DC

This is **func_L204** (incorrectly sized 45 bytes in the auto-disasm — actually runs 118 bytes to file 0x8352).

Verified by raw-byte disassembly of file 0x82DC..0x8351:

### Step 3 — Screen render dispatch

After `set_active_colony` returns, the typical caller pattern is:

```asm
; from func_O014 at file 0x227E8 (line 788)
0x227F2: imul bx, ax, 0x1c                ; ax = unit idx → bx = UnitRecord ptr
0x227F5: mov al, [bx+0x3144]              ; unit.x
0x227F9: sub ah, ah
0x227FB: mov cl, [bx+0x3145]              ; unit.y
0x22801: push cx ; push ax                ; push (x, y)
0x22803: lcall 0x181f:0x7be               ; = find_colony_at_xy_or_fail → file 0x8D26 (func_L239)
0x22808: add sp, 4
0x2280B: or ax, ax
0x2280D: jl 0x2282F                       ; if no colony found, skip
0x2280F: push ax                          ; colony_idx
0x22810: lcall 0x181f:0x9e6               ; = set_active_colony (file 0x82DC)
0x22815: add sp, 2
0x22818: push word [bp-0x40]              ; unit_idx
```

**`lcall 0x191f:0x1de` is the screen-open call.** Its thunk decodes to seg 0x0000:0x11A4 = file 0x35A4, but the bytes there are not a clean function prologue — this suggests segment 0x0000 follows a different base-segment formula than the load-image segments (0x5EB, 0x9EF, etc.), and the actual code lives in **the not-yet-extracted overlay 0x191F** (memory note: "Overlay 0x191F is NOT in viceroy_overlay_full.asm; the main loop body lives there").

## §3. LCALL thunk table — correct resolutions

The thunk table is at **file 0x1A5F0**. Each thunk is 10 or 14 bytes (Type B / Type A respectively).

**Resolution formula for Type B** (verified against the known RNG location):
- Thunk at file `0x1A5F0 + N` for `lcall 0x181F:N`.
- Type B (10 bytes): `9A xx xx 0D 11 | EA <off-lo> <off-hi> <seg-lo> <seg-hi>`.
- Target file = `0x2400 + jmp_seg*16 + jmp_off`.

For `lcall 0x191F:N`, the thunk lives at file `0x1B5F0 + N` (segment 0x191F instead of 0x181F).
For `lcall 0x1A1F:N`, the thunk lives at file `0x1C5F0 + N`.

## §4. What func_O512's 4-loop ACTUALLY is

**Refutes the speculation that `cmp [bp-4], 4` in func_O512 indicates a 4-tile minimap or 4 quadrants.**

From `extracted/disassembly/render_chain_capstone.txt` lines 73-105:

```
0x68023: inc word [bp-4]
0x68026: cmp word [bp-4], 4
0x6802A: jl 0x6802f
0x6802C: jmp 0x6819e                  ; if [bp-4] >= 4, exit loop
0x6802F: mov bx, [bp-4]               ; bx = direction index (0..3)
0x68032: mov al, [bx+0xae]            ; al = dY for this direction
0x68036: cwde
0x68037: mov [bp-0xa], ax             ; save dY
0x6803A: mov cx, ax
0x6803C: mov al, [bx+0xa8]            ; al = dX for this direction
0x68040: cwde
0x68041: mov [bp-2], ax               ; save dX
0x68044: add ax, [0xa5a0]             ; world_x = colony_x + dX
0x68048: mov [bp-0x14], ax
0x6804B: add cx, [0xa5a2]             ; world_y = colony_y + dY
0x6804F: mov [bp-0x18], cx
0x68052: push cx; push ax
0x68054: lcall 0x181f:0x302           ; on_screen(x, y)?
```

Combined with `FUNCTIONS_INVENTORY.md` section B:
- `DS:0xA8` (file 0x1DA48) = 4-dir dX table: `00 01 00 FF` = +0, +1, 0, -1 for N/E/S/W
- `DS:0xAE` (file 0x1DA4E) = 4-dir dY table: `FF 00 01 00` = -1, 0, +1, 0 for N/E/S/W

So **the 4-loop iterates the 4 cardinal-direction neighbors** (N, E, S, W) of the current tile for terrain transition composition. This is the in-game **map terrain renderer**. It has zero connection to the colony screen.

The 3×3 sub-cell composition in the same function uses the 9-byte transition table at DS:0x1EE4 (file 0x1F884) — that's the 3×3 sub-cell pattern for the *terrain tile* (each map tile is composed of 9 sub-sprites), NOT the colony surround 3×3.

## §6. KNOWN UNKNOWNS — what is NOT verified

These are the questions the caller asked which I COULD NOT answer from byte evidence:

### 6a. Entry to the colony screen renderer
- **Verified up to**: `lcall 0x191f:0x1de` from func_O014 at file 0x2281B, and `lcall 0x191f:0x1d0` from func_O015 at file 0x22867. These appear to be sibling entry points — one with 1 arg (unit_idx) and one with 2 args (0, unit_idx) — possibly "open colony screen" vs "open colony screen in build-orders mode".
- **Unknown**: the body of that target function — it's at file 0x35A4 area per the thunk formula, but the bytes there don't decode as a function prologue, suggesting either:
  - The target lives in a non-loaded overlay page (segment 0x191F), or
  - The formula `0x2400 + seg*16 + off` doesn't apply for `jmp_seg=0x0000` thunks (these may use a CS-relative or page-table dispatch).

### 6b. COLONY.PIK background blit
- **Searched**: no `.PIK` string literal in VICEROY.EXE; no direct PUSH of "COLONY" string into the load-image LCALL.
- **Implication**: The `.PIK` filenames are constructed at runtime by concatenating a base name. The base name "COLONY" appears at file 0x1FA82 — but that one is the COLONY.SAV builder (next bytes are `.SAV\0`). Screen-`.PIK` filename construction lives in overlay 0x191F.

### 6c. Surround minimap loop count (3×3 vs 4-quadrant)
- The current Python port uses 3×3 = 9 tiles.
- The closest match in available disasm is **`func_O108`** at file 0x2D30A (outer loop 0..4, inner loop 0..5, evaluating `[bx]+i-2`, `[bx+1]+j-2`) — that's a 5×6 = 30-tile scan with filter, NOT 9. It is probably the **city-wall fire-arc** or similar gameplay-radius scan, not the visible 3×3 surround.
- **The visible 3×3 surround code is in overlay 0x191F.**

### 6d. Production-row sprite indices (bell / cross / anvil)
- **No byte evidence found** in the available disasm for "bell sprite index N is blitted at colony-screen position X".
- The ICONS.SS catalog already documents bell at index 3, cross at index 4, anvil/hammer at index 6 (per `SESSION_UI_CATALOG.md` and `extracted/sprites/`). These need to be re-verified by reading the byte sequence in the actual renderer function — which is in overlay 0x191F.

### 6e. Colonist mid-band sprite index
- **No byte evidence found** for the specific mid-band colonist sprite source.
- Memory notes confirm unit-on-map sprites come from ICONS.SS index 100..105 + 109 (foot units). For the colony-screen mid-band specifically, the byte trace is in overlay 0x191F.

### 6f. Stockpile (16 cells, cell-width, qty draw position/color)
- ColonyRecord stockpile at `+0x9A..+0xB9` (16 × u16) is byte-verified per `DATA_MODEL.md`.
- The blit/draw geometry (X position per cell, font color thresholds) is in overlay 0x191F.

### 6g. Building draw loop, BUILDING.SS index
- ColonyRecord has building bytes per `DATA_MODEL.md` (offsets TBD per session memory).

## Appendix B — Why "[0x8542] = cur_nation" tag is wrong

The `viceroy_overlay_full.asm` file annotates `mov bx, [0x8542]` with `; cur_nation` comment. This is an automated tag from `function_index.json` propagation. It is **wrong**:

1. If `[0x8542]` were `cur_nation` (an integer 0..3 or 0..11), then `mov bx, [0x8542]` would put 0..11 in BX, and subsequent `mov al, [bx+0x1F]` would dereference DGROUP[0..11 + 0x1F] = DGROUP[0x1F..0x2A] — meaningless data.
2. Instead, `[0x8542]` IS a NEAR pointer set by `set_active_colony` to point at a ColonyRecord. `[bx+0x1F]` = colony.size, `[bx+0x9A]` = colony.stockpile[0], `[bx+0x1A]` = colony.owner_power, etc. — all match `DATA_MODEL.md`.
3. The actual `cur_nation` index is at `[0x5398]` (memory note 2026-04-20: "DS:0x5398 is the current_nation_index at turn start").

The `; cur_nation` tag in the disasm should be globally search-replaced with `; *Colony (active)` or `; colony_ptr`. (Did not make this change — informational only.)
