# VICEROY.EXE — source-module reconstruction

**What this is.** The list of source modules Sid Meier's Colonization
(`VICEROY.EXE`, 1994) was built from — what each module is responsible
for and where it lives in the executable. Unlike its sibling
`MAPEDIT.EXE`, VICEROY shipped **without CodeView debug symbols**, so its
module structure was never recorded and is reconstructed here from three
evidence layers (see *Method* at the end). Generated by
`tools/rtlink/make_module_map.py` → `data_extracted/viceroy_modules.json`.

## How the executable is built

VICEROY is a Microsoft C 6.0 program linked with **RTLink/Plus overlays**.
The file is a DOS MZ image in three parts:

1. **Resident load image** (file `0x2400`–`~0x20000`): always in memory —
   the C runtime, the resident half of the MADS/MPS engine library, and
   the resident game core (unit/colony/turn state helpers).
2. **31 overlay pages** (`0x01`–`0x1F`, file `0x20EE0`–`0x78D40`): swapped
   in on demand. Each page is one linker grouping of game or engine
   modules; the byte-exact page directory is at file `0x192F0`
   (`tools/rtlink/viceroy_rtlink_map.json`). Code in a page is reached
   through **thunk segments** (`0x181F`/`0x191F`/`0x1A1F`/`0x0D1D`/`0x0C0C`)
   — a near stub that asks the RTLink loader to page in the target.
3. **DGROUP data segment** — all globals and the record tables
   (`ColonyRecord` stride `0xCA`, `UnitRecord` `0x1C`, `PowerRecord`
   `0x13C`, `NativeSettlement` `0x12`; see `tools/viceroy_symbols.json`).

The codebase is **two layers**, exactly as MAPEDIT's symbols show for the
same studio: a shared **MADS/MPS engine library** (memory, EMS/XMS,
MADSPACK decompression, palette, mouse, the `.FF`/`.PIK`/`.SS` loaders, the
popup/dialog framework, the C runtime) and the **game layer** on top. The
engine modules recur in VICEROY nearly byte-for-byte, which is what lets
them be named at all (below).

## Coverage

- **1250** functions total.
- **89** carry a real 1994 name + module (tier **B**, from
  the MAPEDIT fingerprint match).
- **754** attributed by same-module run or page-level
  mechanic identity (tier **A**).
- **27** are overlay page-header / relocation data mis-split as functions
  (tier DATA).
- **260** resident-image functions remain unattributed
  (no name anchor and no clean band) — the residual, honestly marked.

## Method & evidence tiers

Per `notes/TRUTH_HIERARCHY.md`:

- **B (byte-verified):** the function carries a real CodeView name matched
  from MAPEDIT by instruction fingerprint
  (`data_extracted/viceroy_named_from_mapedit.json`, 89 exact matches).
  MAPEDIT's own symbols are re-extracted reproducibly by
  `tools/extract_codeview.py` → `data_extracted/mapedit_symbols.json`
  (211 modules, 1071 publics).
- **A (inferred):** either an unanchored function lying between two
  same-module B-anchors (contiguous link layout), or an overlay function
  taking its page's mechanic identity from the GAME.TXT emitter map
  (`tools/rtlink/event_emitters.json`) + the prose screen attributions
  (`docs/UI_PHASE1_ATTRIBUTION.md`, `docs/UI_AUDIT_TRACKER.md`,
  `notes/ATTRIBUTION_OVERLAY.md`).
- **DATA / TBD:** overlay page-header regions mis-split as functions, and
  resident functions with neither anchor — left honestly unattributed.

The inferred module names (`*`) are the mechanic, not a claim about the
original `.obj` filename — those are unrecoverable without symbols. The
machine form with every function's assignment is
`data_extracted/viceroy_modules.json`.
